# Оптимизация загрузки Club PWA

## Цель

Ускорить холодный и повторный запуск приложения без изменения бизнес-логики и внешнего вида. Основной результат должен быть измерим по production-сборке, сетевой загрузке и браузерным метрикам, а не только по структуре исходного кода.

## Исходное состояние

Production-сборка от `1be83a0` загружает на первом экране один JS-файл размером 395 845 байт (123 277 байт gzip) и один CSS-файл размером 553 182 байта (80 299 байт gzip). Lighthouse на локальной production-сборке показал performance 0,89, FCP 2 334 мс, LCP 2 561 мс и около 90 KiB неиспользуемого JavaScript. Главная причина — общий API-модуль всех продуктовых разделов попадает в стартовый граф зависимостей; CSS сообщества также загружается до открытия чата.

## Рассмотренные подходы

1. Рекомендуемый консервативный подход: отделить минимальный startup API от API ленивых разделов, загружать CSS сообщества вместе с разделом, сделать редкие глобальные экраны асинхронными и закрепить бюджеты production-сборки. Он даёт заметное уменьшение первого ответа при низком риске регрессий.
2. Полное разделение `App.vue` и монолитного `styles.css` по каждому маршруту. Потенциальный выигрыш выше, но одновременное перемещение десятков тысяч строк CSS и всей оболочки создаёт непропорциональный риск визуальных и мобильных регрессий.
3. Только серверное кеширование. Оно ускоряет повторные загрузки, но не уменьшает холодный старт и не устраняет неиспользуемый стартовый JavaScript.

Выбран подход 1. Большое структурное разделение оболочки откладывается до отдельной миграции с покомпонентным визуальным контролем.

## Архитектура

- `api/http.ts` становится единственной точкой настройки `ofetch`, заголовков preview/PWA и базового URL.
- `api/startup.ts` содержит только запросы, которые нужны оболочке, авторизации, сессии и уведомлениям до открытия ленивого раздела.
- `api/client.ts` сохраняет публичный контракт продуктовых разделов, использует общий HTTP-клиент и переэкспортирует startup-функции для обратной совместимости.
- `App.vue`, session store и notifications store импортируют `api/startup.ts` напрямую, поэтому Rollup не обязан включать весь `client.ts` в entry chunk.
- `community.css` импортируется из ленивого `CommunitySection.vue`, а не из `main.ts`.
- Редко показываемый центр уведомлений становится асинхронным компонентом.
- Скрипт бюджета анализирует реальные gzip-размеры entry-файлов из `dist/index.html` после production-сборки.

## Бюджеты

- entry JavaScript: не более 105 000 байт gzip;
- entry CSS: не более 78 000 байт gzip;
- сумма entry JS и CSS: не более 180 000 байт gzip;
- проверка запускается автоматически после `vite build` и блокирует регрессирующую сборку.

Бюджеты ниже подтверждённого baseline, но оставляют небольшой запас для штатного развития продукта.

## Кеширование и PWA

Versioned assets продолжают получать `immutable` на сервере и кешируются Service Worker только после успешного same-origin ответа. HTML, API и Service Worker не получают долгоживущий кеш. Версия кеша увеличивается при выпуске оптимизации, чтобы клиенты не удерживали старый entry bundle.

## Проверка

- RED/GREEN-тест анализатора bundle-бюджета;
- production-сборка до и после изменений с фиксацией gzip-размеров;
- `pnpm check`, полный `pnpm test`, `pnpm build`, release E2E;
- Lighthouse и сетевой список запросов на production-preview;
- визуальный Playwright-аудит 320, 390, 768, 1024 и 1440 px;
- после деплоя — commit marker, состояние контейнеров, `/api/health`, HTML и Service Worker production-сайта.

## Ограничения

Оптимизация не меняет API-контракты, платежи, авторизацию, темы и пользовательскую навигацию. Монолитный legacy CSS остаётся главным последующим кандидатом на постепенную декомпозицию, но не переписывается целиком в этом проходе.
