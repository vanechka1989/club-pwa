# Комплексное усиление Club PWA

## Цель

Устранить подтверждённые аудитом слабые стороны приложения без переписывания продукта: восстановить стабильность интерфейса, закрыть приватные медиа, сделать статистику корректной при росте аудитории, ограничить злоупотребления, улучшить масштабируемость API и усилить обязательные проверки перед релизом.

## Границы работы

В работу входят:

- device-mode и PWA-install UX;
- регрессии тем и маршрутов оплаты;
- авторизация локальных медиа и политика кеширования;
- корректные SQL-агрегации административной статистики;
- пагинация поддержки, сообщества и тяжёлых административных выборок;
- rate limiting для продуктовых write-endpoints;
- обязательный release E2E-набор;
- локальное уменьшение самых крупных точек связанности и начального frontend-бандла;
- проверка зависимостей, PWA, доступности и производительности.

Не входят смена Vue/Hono/Drizzle, редизайн продукта, изменение платёжной бизнес-логики и полная переработка всех крупных файлов за один проход.

## Подход

Работа выполняется последовательными безопасными слоями. Каждый слой начинается с воспроизводящего теста, вносит минимальное изменение и завершается проверкой затронутого пакета. Рефакторинг выполняется только после восстановления поведения и не меняет публичные контракты без необходимости.

## 1. PWA и интерфейс

Device-mode предупреждение перестаёт быть блокирующим для уже доступной пользовательской оболочки. Определение устройства используется как рекомендация по представлению, а не как контроль доступа. Продолжение работы сохраняется устойчиво, тестовые и реальные desktop-сценарии не перекрываются модальным слоем.

Backend не считает `X-Club-PWA-Standalone` доказательством безопасности. Заголовок остаётся диагностическим сигналом совместимости, но вход и сессионные endpoints защищаются реальной сессией, origin/cookie-политикой и rate limiting.

Регрессии тем и `/payments/provider` исправляются по их фактическим причинам. Обязательные проверки охватывают четыре семантические темы, desktop, Android и iOS, основные разделы, платежные настройки и административные task screens.

## 2. Приватные медиа

Локальные файлы больше не выдаются публичным маршрутом без проверки. Запрос медиа связывается с сущностью-владельцем и текущим пользователем:

- материалы обучения доступны активному участнику и администраторам с правом управления материалами;
- вложения поддержки доступны владельцу обращения и администраторам поддержки;
- медиа сообщества доступны пользователям с доступом к соответствующей теме;
- административные и резервные объекты не выдаются общим media endpoint.

Публичное долгосрочное кеширование заменяется приватной политикой. Для object storage используются короткоживущие подписанные URL; публичный base URL не применяется к приватному контенту. Отзыв доступа должен прекращать получение новых файлов и URL.

## 3. Статистика и списки

Сводные показатели считаются SQL-агрегациями по полной базе, независимо от страницы списка пользователей. `totalUsers`, `activeUsers` и суммарный прогресс имеют отдельные точные запросы.

Пользователи, тикеты, сообщения, опросы и административные журналы получают cursor-pagination с ограниченным размером страницы. API временно сохраняет существующие поля ответа там, где frontend ещё ожидает их, но добавляет `nextCursor` и переводит интерфейс на дозагрузку. Максимальные лимиты задаются схемой и не принимаются напрямую от клиента без ограничения.

## 4. Защита от злоупотреблений

Ограничения применяются к созданию сообщений, обращений, комментариев и загрузок. Ключ строится из user ID и категории операции, а для анонимных endpoints — из доверенного IP. Production-хранилище лимитов должно работать между экземплярами API; PostgreSQL используется как надёжный baseline, Redis может ускорять realtime-сценарии при наличии.

Превышение лимита возвращает `429`, стабильный машинный код и `retryAfterSeconds`. Размер текста, число файлов, MIME, декодированный размер изображения и длительность/размер аудио проверяются до тяжёлой обработки.

## 5. Архитектура и производительность

Первым извлекается только код, непосредственно затронутый исправлениями: device-mode policy, административные агрегаты, media authorization и pagination helpers. Большие Vue-компоненты делятся по самостоятельным task screens и composables только если это уменьшает область изменяемого поведения.

QR-генератор загружается динамически только при показе desktop-подсказки. Release notes и административные экраны остаются lazy-loaded. Общий CSS не переписывается целиком: новые и изменяемые стили переводятся на существующие семантические токены, явные дубли удаляются после визуальной проверки.

Service worker сохраняет безопасный network-first режим для API, кеширует versioned assets и предоставляет предсказуемую offline-оболочку без кеширования приватных API-ответов.

## 6. Ошибки и наблюдаемость

Ошибки авторизации медиа возвращают `404`, чтобы не раскрывать существование объекта. Ошибки лимитов и валидации имеют стабильные коды. Фоновые ошибки удаления и кеширования логируются без секретов и персональных URL.

Метрики дополняются счётчиками `429`, отказов media authorization и длительности тяжёлых административных запросов. Логи не содержат session cookie, подписанные URL или ключи провайдеров.

## 7. Проверка результата

Обязательные критерии:

- `pnpm check`, `pnpm test` и `pnpm build` завершаются успешно;
- release E2E покрывает desktop, Android и iOS, темы, оплату и ключевые task screens;
- расширенный desktop-профиль проходит без блокирующего device-mode слоя;
- приватный файл недоступен без сессии, после отзыва доступа и пользователю другой сущности;
- статистика корректна при более чем 200 пользователях;
- списки не возвращают неограниченную историю;
- превышение write-rate возвращает `429` и корректный retry interval;
- на ширинах 320, 390, 768, 1024 и 1440 нет горизонтального переполнения и недоступных основных действий;
- service worker не кеширует приватные API-ответы;
- dependency audit либо проходит, либо фиксирует конкретную внешнюю причину невозможности проверки.

## Совместимость и миграция

Изменения схемы выполняются отдельными Drizzle-миграциями, совместимыми с текущими данными. Старые локальные object keys сохраняются и получают метаданные доступа через существующие связи. Развёртывание не требует одновременного удаления старых полей ответа: backend сначала добавляет новые контракты, frontend переходит на них, затем устаревшее поведение удаляется отдельным последующим изменением.

## Риски

Главный риск — нарушение отображения существующих медиа после закрытия публичного маршрута. Он снижается тестами всех типов вложений и совместимым resolver для старых ключей. Второй риск — рост времени полного E2E; обязательный release-набор остаётся компактным, но репрезентативным, а полная матрица продолжает запускаться по расписанию.
