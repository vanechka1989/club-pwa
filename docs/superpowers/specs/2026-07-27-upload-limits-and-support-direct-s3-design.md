# Upload Limits And Support Direct S3 Design

## Goal

Protect the API from buffered oversized multipart requests while allowing avatars up to 10 MiB, support attachments up to 50 MiB each and 100 MiB per message, without changing the existing large lesson upload flow.

## Scope

- Profile avatar uploads remain `multipart/form-data` and are limited to 10 MiB.
- All customer and administrator support attachments use a short-lived same-origin PUT URL and are streamed by the API into S3 without multipart parsing or full-body buffering.
- A support message accepts at most four attachments, at most 50 MiB each, and at most 100 MiB total.
- Existing learning upload endpoints, multipart part sizing, and lesson limits are unchanged.
- Proxy limits are route-specific. No global 50 MiB API limit is introduced.

## Architecture

### Avatar flow

The client validates file size and image type before submission. The reverse proxy rejects an oversized avatar request before it reaches Bun. The API retains its own 10 MiB validation as defense in depth, parses the bounded multipart form, optimizes the image, and writes it to S3.

### Support attachment flow

1. The authenticated client requests an upload intent with file name, MIME type, and declared size.
2. The API validates access, per-file constraints, media type, and the 50 MiB maximum. It creates a user-scoped `support/pending/` object key and returns a same-origin PUT URL valid for ten minutes.
3. The browser uploads bytes to the bounded PUT route. Caddy rejects bodies above 53 MB (allowing an exact 50 MiB file) and the API verifies the exact declared `Content-Length` and type before streaming the request into S3.
4. The client submits the ticket or reply as JSON containing message fields and uploaded-object references.
5. Before writing attachment records, the API reads S3 metadata and verifies the object key namespace, ownership token, content type, non-zero size, declared size, 50 MiB per-file limit, and 100 MiB total limit.
6. Failed or abandoned uploads remain unreferenced and are deleted by a scheduled cleanup policy.

The API never accepts support video bytes through `formData()` or `arrayBuffer()`. This avoids the Beget S3 browser-CORS restriction while keeping Bun memory bounded. Existing read URLs and the seven-day support attachment expiry behavior remain unchanged.

## Isolation From Learning Uploads

Learning media keeps its existing `/api/admin/learning/materials/uploads/*` single-part and multipart contracts. Reverse-proxy rules match the avatar endpoint specifically, while JSON control requests and direct S3 traffic do not inherit that body limit. The learning multipart proxy, if retained, keeps its existing per-part limit rather than the avatar limit.

## Security And Error Handling

- Upload intents require the same authenticated support access as ticket creation or replies.
- Object keys are generated by the API and cannot be chosen by the client.
- Upload URLs expire after ten minutes and authorize one authenticated, user-scoped object key, size, and content type.
- Finalization rejects missing, expired, oversized, mismatched, foreign, or already-consumed objects.
- A failed message creation does not create attachment database rows.
- Client-visible errors distinguish unsupported type, 50 MiB per-file overflow, 100 MiB total overflow, expired upload, and storage failure.
- Rate limiting covers upload-intent creation and message finalization.

## Compatibility

The web client migrates all support submission paths together: new ticket, customer follow-up, administrator reply, and administrator-created ticket. Legacy multipart support endpoints may be accepted only during the same-release transition and must retain an early proxy cap; once the deployed client uses direct upload, multipart attachment handling is removed.

## Testing

- Unit tests prove avatar limits are exactly 10 MiB on client and API.
- API tests cover upload intent validation, user-scoped keys, S3 metadata verification, ownership, consumption, per-file and total limits.
- Web tests cover direct upload sequencing, progress/error recovery, and every support submission path.
- Deployment configuration tests prove the avatar body limit is route-specific and does not match learning upload routes.
- Existing learning upload and release E2E suites must remain green.

## Success Criteria

- A request exceeding the avatar route cap receives HTTP 413 before multipart parsing.
- Support files are streamed through Bun and never buffered in full.
- A valid 50 MiB support video can be attached successfully.
- More than 50 MiB per file or 100 MiB per message is rejected.
- Existing large lesson uploads behave exactly as before.
