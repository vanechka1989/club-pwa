# Ленивые CSS-чанки пользовательских разделов

## Цель

Сократить стартовый CSS Club PWA, не меняя визуальный дизайн, бизнес-логику и публичные контракты. Экранные правила должны загружаться вместе с уже ленивыми Vue-разделами, а общая оболочка, темы и смешанные правила остаются в стартовом CSS.

## Рассмотренные подходы

1. **Строгое извлечение по селекторам — выбранный подход.** PostCSS переносит правило только тогда, когда каждый селектор правила однозначно принадлежит одному разделу. Смешанные правила остаются глобальными. Это даёт наибольшее уменьшение стартового CSS при контролируемом риске.
2. **Ручной перенос только поздних цельных блоков.** Проще визуально проверить, но большая часть экранного CSS останется в стартовом чанке, а правила одного раздела продолжат быть разбросаны по файлу.
3. **Полная миграция на scoped CSS/CSS Modules.** Даёт лучшие архитектурные границы, но требует перепроверки тысяч селекторов и выходит за рамки безопасной оптимизации загрузки.

## Архитектура

`splitRouteCss.mjs` получает исходный CSS и карту разделов. Для каждого CSS-правила он разбирает список селекторов полноценным selector parser, а не разделением строки по запятым. Правило переносится только если все его селекторы имеют ровно одну и ту же маршрутную принадлежность. Вложенные `@media`, `@supports` и другие контейнеры клонируются в маршрутный файл с сохранением порядка. Пустые контейнеры удаляются.

Маршрутные файлы создаются для `profile`, `learning`, `support`, `billing`, `admin`, `notification` и `community`. Они импортируются непосредственно соответствующими ленивыми Vue-компонентами. Уже существующий `community.css` остаётся владельцем сообщества и получает извлечённые правила как отдельный сгенерированный соседний файл, чтобы не смешивать ручной и механически выделенный CSS.

Исходный `styles.css` после одноразового разбиения остаётся обычным редактируемым файлом. Скрипт поставляется как проверяемый инструмент для воспроизводимости операции, но production-сборка не переписывает исходники.

## Безопасность каскада

- Правило с глобальным селектором или селекторами нескольких разделов не переносится.
- Порядок правил внутри каждого маршрутного файла сохраняется.
- Ключевые кадры, шрифты, custom properties, базовые элементы, темы и общая оболочка остаются глобальными.
- Маршрутный CSS загружается после общего CSS. Это соответствует назначению экранных правил и сохраняет поздние экранные уточнения; визуальная эквивалентность отдельно проверяется матрицей Playwright.
- Если правило не удаётся однозначно классифицировать, оно остаётся в `styles.css`.

## Бюджеты

После разбиения production build обязан соблюдать:

- entry JavaScript gzip не более 105,000 байт;
- entry CSS gzip не более 55,000 байт;
- combined entry gzip не более 155,000 байт;
- ни один маршрутный CSS-файл не должен быть включён ссылкой в `index.html`.

Порог CSS оставляет запас относительно ожидаемого результата и предотвращает возврат экранных правил в стартовую загрузку.

## Проверка

Скрипт разбиения покрывается fixture-тестами: однозначные правила извлекаются, смешанные остаются, вложенные at-rules сохраняются, запятые внутри `:is()` не ломают классификацию. Затем выполняются typecheck, полный unit/component suite, production build, release E2E, device viewport suite и Lighthouse. Визуальные проверки охватывают 320, 390, 768, 1024 и 1440 пикселей, Android, iOS WebKit, темы и основные маршруты.

## Ограничения

Работа не меняет визуальный дизайн и не пытается полностью устранить историческое дублирование CSS. Оставшиеся смешанные правила — отдельный архитектурный долг, который безопаснее сокращать последующими локальными рефакторингами компонентов.
